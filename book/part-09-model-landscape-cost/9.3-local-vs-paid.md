# Local vs. paid

## Why this matters

Local models cost nothing per token, so it is tempting to call them free. They are not: you pay in memory, in speed, in quality on hard tasks and in your own time. Paid models invert that: you pay per token and get quality and speed you could not run at home. Neither side wins in general. What you can do is measure both on your own tasks and write down where each one wins, which is the point of this chapter and of the routing rules in [9.4](/part-09-model-landscape-cost/9.4-routing-rules).

You already hold most of the data. [Experiment 00](https://github.com/hsavovski/ai-engineering/tree/main/experiments/00-speed-check) measured Qwen speed and memory on your Mac, the local-harness practice in [5.5](/part-05-harnesses/5.5-harnesses-local-qwen) tests local models in agent loops, and [9.1](/part-09-model-landscape-cost/9.1-paid-apis) gave you paid-model pass rates and cost per passed task. This chapter tells you how to read those numbers side by side and what is still missing from them.

**Learning goals**

- Compare local and paid models on quality, speed and total cost
- Identify tasks local models handle well
- Understand privacy and offline benefits

## Explanation

### Compare on your tasks, not on leaderboards

A public benchmark tells you how a model does on someone else's tasks. Chip Huyen's *AI Engineering* treats the build-versus-buy decision (self-hosting a model against calling an API) as part of model selection, under Chapter 4 "Evaluate AI Systems" ([table of contents](https://github.com/chiphuyen/aie-book/blob/main/ToC.md)). The workable method is the same as in 9.1: a small set of your own tasks with automatic checks, run against each candidate, reporting **pass rate**, **latency** and **cost per passed task**.

For local models the three numbers behave differently from paid ones:

| | Paid API | Local (Ollama on your Mac) |
|---|---|---|
| **Pass rate** | Varies by tier; the flagship sets the ceiling | Varies by size and quantization; the ceiling is what fits in memory |
| **Latency** | Network plus queueing plus generation; scales with the provider's load | Load time on first call, then generation; no network, but one machine shared with everything else you run |
| **Cost** | Metered: `usage` fields times a price (see [Landscape](/landscape)) | Not metered: electricity, hardware you already own, and your time |

Because local cost per token is near zero, the interesting local number is not cost per task but **cost per passed task including the failures**: a free model that passes 40% of tasks costs you the other 60% in retries, review time or a paid fallback.

### Quality: the gap is a function of the task

Two results from your own lab show the shape. In experiment 00, `qwen3:8b` wrote code with a subtle bug that looked right at a glance, while `qwen3:14b` and `qwen3:30b-a3b` wrote it correctly. Same prompt, three sizes, three outcomes. That is one task and one run, so it is an anecdote, not a rate, but it points at where the gap lives: not on simple, well-specified work, but on tasks that need care, long chains of reasoning or reliable tool calls.

A useful way to sort tasks, before you measure anything:

- **Likely fine locally:** classification and extraction with a clear schema, short summaries, rewriting, commit messages, simple code transformations, embeddings, and anything you can check automatically and retry cheaply.
- **Likely to need a paid model:** multi-file code changes, long agent runs where one wrong tool call derails everything, hard reasoning, and tasks where a wrong answer is silent (you cannot tell it is wrong).
- **Unknown until you test:** most of your actual workload. That is what the practice fills in.

Treat these as hypotheses to confirm with pass rates, not as rules. Model quality at a given size has moved fast, and the 14b-class model you run today may handle things the same class could not a year ago.

Two local-specific traps spoil comparisons. First, **configuration**: Ollama's default context window is 4096 tokens ([Ollama FAQ](https://docs.ollama.com/faq)), so a long prompt can be silently cut off and you would blame the model for what is a setting. Set `num_ctx` explicitly and record it ([1.9](/part-01-how-llms-work/1.9-kv-cache-context-window)). Second, **thinking**: experiment 00 saw a simple answer go from 2 seconds to 45 seconds with thinking on, and `qwen3:30b-a3b` leaked reasoning text into the answer with `think: false`. A pass rate that ignores the thinking setting is not comparable with a paid model's setting ([1.10](/part-01-how-llms-work/1.10-reasoning-models)).

### Speed and memory on a 24 GB Mac

Your Mac mini has 24 GB of unified memory shared by the CPU, the GPU and macOS. For a model that fits, speed is set mostly by one thing: generating each token reads the active weights from memory once, so the ceiling is roughly **memory bandwidth divided by the bytes read per token**. Apple lists the M4 Pro at 273 GB/s ([Apple newsroom](https://www.apple.com/newsroom/2024/10/apple-introduces-m4-pro-and-m4-max/)). That is a ceiling for planning, not a prediction: real speed is lower, and you measure it.

Check the shape against your own numbers from experiment 00 (all Q4, thinking off):

| Model | Weights in memory | Output tok/s | Reading |
|---|---|---|---|
| qwen3:8b | 5.2 GB | ~41 | Dense: about 8B parameters read per token |
| qwen3:14b | 9.7 GB | ~25 | Dense: nearly twice the bytes, about 60% of the speed |
| qwen3:30b-a3b | 19 GB | ~41 | MoE: ~3B parameters active per token, so as fast as the 8b |

This is the active-parameter rule from [1.11](/part-01-how-llms-work/1.11-mixture-of-experts) at work, and the memory column is the cost: every expert must be loaded, so the 30b-a3b takes 19 GB, spilled 6% to the CPU in your measurement, and left 14% of memory free. A model that "fits" but leaves no room for your editor, browser and the KV cache makes the whole machine slow. For the memory arithmetic see [1.12](/part-01-how-llms-work/1.12-quantization); for what is measured on your Mac, see [Landscape](/landscape#what-fits-in-24-gb-of-unified-memory).

Three more speed facts that change the comparison:

- **Prompt processing is separate from generation.** Long prompts (an agent re-sending its whole history every turn) cost prefill time on a local machine, not just on a metered API. Experiment 00 reported prompt speeds in the tens to low hundreds of tokens per second; a 20k-token agent context is therefore tens of seconds before the first token, unless the prefix is cached.
- **One machine, one queue.** Ollama keeps a model loaded for 5 minutes by default and, per its FAQ, parallel requests multiply the context memory (`OLLAMA_NUM_PARALLEL` times the context length). Several agents hitting the same model at once do not scale the way a hosted API does.
- **Paid models are usually faster on hard tasks.** A hosted model generates more tokens per second and is less likely to need a retry. The exception is small, well-specified work, where a local call with no network round trip and no queue can finish sooner. Measure both.

### True cost

A local model has no price per token, but running it is not free. Make the cost visible by listing every component:

1. **Electricity.** Apple's power table for the Mac mini lists an idle draw of 5 W and a maximum of 140 W for the M4 Pro configuration it shows ([Apple Support](https://support.apple.com/en-us/103253)). Your real draw during generation is somewhere between them; a plug-in power meter tells you. A worked example with **made-up numbers**: suppose generation averages 60 W and your electricity costs 0.30 per kWh. One hour of generation at 25 tok/s produces 90,000 tokens and uses 0.06 kWh, which costs 0.018: about 0.20 per million output tokens. Compare that, per million tokens, with the output prices on [Landscape](/landscape) and note two things. The electricity is small next to the metered prices of the larger models, and it is not the biggest local cost.
2. **Hardware.** You already own the Mac mini, so the marginal cost is zero, but only while the model fits and the machine has spare time. If running a model forces an upgrade, or you buy a machine for it, the cost is the purchase price spread over the tokens you actually generate. A machine that sits idle 95% of the day has an expensive token.
3. **Time.** Waiting 45 seconds for a thinking answer, babysitting a model that leaks reasoning into its output, and reviewing wrong answers all cost you attention. If you value your time at any real rate, this usually dominates electricity. It is why "free" local models can lose on cost per passed task.
4. **Opportunity cost of memory.** While a 19 GB model is loaded, the rest of your Mac works with 5 GB.
5. **Maintenance.** Updating Ollama, pulling and re-testing models, templates and quirks ([10.1](/part-10-modifying-serving-models/10.1-ollama-modelfile)).

The honest summary: local wins on **marginal cost at volume**, paid wins on **cost of a wrong answer and of your time**. The break-even depends on your volume and your pass rates, so compute it, do not guess it:

```
paid cost per passed task   = (tokens_in x price_in + tokens_out x price_out) / pass_rate_paid
local cost per passed task  = (electricity per task + your time per task x your rate) / pass_rate_local
```

Put your own time cost in the second line, even as a rough number. If you leave it out, local always looks cheaper.

### Privacy and offline

With local inference your prompts stay on the machine: Ollama's FAQ says "We don't see your prompts or data when you run locally", and it binds to `127.0.0.1` by default, so other machines cannot reach it unless you change `OLLAMA_HOST` ([Ollama FAQ](https://docs.ollama.com/faq)). That is a different kind of guarantee from a paid provider's policy. A policy says what the provider promises to do with data it has received. Local means the data was never sent. Chapter 9.1's [privacy table](/part-09-model-landscape-cost/9.1-paid-apis#data-and-privacy-policies) shows how much those policies differ by route, and that for some providers I could not confirm the terms at all.

Two cautions:

- **"Ollama" does not always mean local.** Ollama also offers cloud models that run on its servers; for these it states it processes prompts and responses to answer requests and does not use them to train models, but it does not state a retention period on that page ([Ollama cloud docs](https://docs.ollama.com/cloud)). A model name with a `:cloud` suffix leaves your machine. Check which one you are calling, and the FAQ explains how to disable cloud features.
- **Local does not mean private end to end.** A local agent that fetches web pages, calls an MCP server or logs prompts to a tracing service still sends data out. The model is local; the system around it may not be. This is the same boundary Part 8 discusses for security.

**Offline** is the other benefit: no network, no outage, no rate limit, no account, and no bill. It matters on a plane, in a locked-down environment, or when a provider is down. Offline also means no provider-side updates: the model you tested is the model you get next month, which helps reproducibility and means nobody improves it for you.

### When local wins

Put the pieces together. Local is the better choice when most of these hold:

- the task is simple and checkable, so a 14b-class model passes it reliably;
- the volume is high, or the task runs in the background, so per-token fees would add up and latency does not matter;
- the data is sensitive, or you are not allowed to send it out;
- you need to work offline, or you want a fixed, reproducible model;
- you are iterating on a prompt or a pipeline and want to make hundreds of throwaway calls.

Paid is the better choice when the task is hard, long or agentic, when a wrong answer is expensive or silent, when you need a large context window, or when your time is the scarce resource. In practice the answer is rarely one or the other: it is a **routing rule** that sends each task type to the cheapest model that passes it, with a paid fallback. Writing that rule down is [9.4](/part-09-model-landscape-cost/9.4-routing-rules), and this chapter's practice produces its input.

## Practice

**Brief:** Combine results from 5.5 and 9.1 into one table in `notes/routing.md`: task type x model -> pass rate, speed, cost.

**Where:** Notes only, no code (`notes/`).

**Steps**

1. **Gather your sources.** Open the results of the local-harness practice (5.5), the model-mix experiment (`experiments/34-model-mix/README.md`, from 9.1) and the speed check (`experiments/00-speed-check/README.md`). If one is missing, run it first or mark that column "not measured". Do not fill a gap with a number you did not measure.
2. **Define task types.** Group your tasks into three to six types, for example "small code fix", "extraction to a schema", "multi-step agent task". Write one line per type on how it is checked. A task belongs to exactly one type.
3. **Pick the models.** At least two local models (say a 14b dense and the 30b-a3b) and at least two paid models from the 9.1 run, each with its thinking setting and `num_ctx` or `max_tokens` noted.
4. **Build the table** in `notes/routing.md`, one row per task type and model, with columns: pass rate (passed/attempted, not just a percent), median speed (tokens per second or seconds per task), cost per task, cost per passed task. For local models, write the electricity estimate and your assumptions in a line above the table; do not hide it in the cost column.
5. **Add your time.** For each local row, add a rough "my time per failed task" and say what it assumes. Then compute the break-even for one task type with the formula in "True cost".
6. **Mark the gaps.** Cells you could not measure get "?" and a note on what would fill them. Small samples (under about 10 attempts) get a warning.
7. **Write the rule candidates.** Under the table, write one sentence per task type: the cheapest model that clears the bar you picked, and the bar. This feeds 9.4.

**Done when:**

- `notes/routing.md` has the table with real recorded numbers (or explicit "?" marks) for at least two local and two paid models across at least three task types.
- Every row states the model's thinking setting and context or token cap.
- Cost per passed task is computed for every filled row, and the local rows state their assumptions about electricity and time.
- There is a break-even calculation for one task type.
- You wrote, without looking at a leaderboard, which task type surprised you most and why.

## Check questions

1. A local 14b model passes 40% of a task type and a paid mid-tier model passes 95%. Why can the local model still be the cheaper choice, and what would make it more expensive?

   <details><summary>Answer</summary>

   Local cost per passed task is (electricity + your time per task) divided by the pass rate, and electricity is tiny, so it can win if failures are cheap to detect and retry (an automatic check, a background job). It loses when failures are silent or when each failure costs you review time, because your time is the largest local cost. Also compare with the paid cost per passed task, not per-token price alone.

   </details>

2. Why does `qwen3:30b-a3b` generate about as fast as `qwen3:8b` on your Mac, and what does it cost you instead?

   <details><summary>Answer</summary>

   Decoding speed is bounded by the bytes read per token, and the MoE reads only about 3B active parameters per token. The cost is memory: all experts must be loaded, so it takes about 19 GB of 24 GB (6% spilled to the CPU in experiment 00), leaving little for the KV cache and other apps.

   </details>

3. Your local model "fails" a long-prompt task that a paid model passes. Name two non-quality causes to rule out before concluding the model is worse.

   <details><summary>Answer</summary>

   The context window: Ollama's default is 4096 tokens, so the prompt may have been truncated unless `num_ctx` was set. The thinking setting: thinking on can consume the output budget or slow the run, and thinking off can leak reasoning text into the answer, which a checker may reject. Also check memory spill to CPU and the quantization.

   </details>

4. State precisely what "my data stays local" means with Ollama, and give two ways it can be false.

   <details><summary>Answer</summary>

   Prompts are processed on your machine and Ollama says it does not see them, with the server bound to 127.0.0.1 by default. It is false if you call a `:cloud` model (it runs on Ollama's servers), if you expose `OLLAMA_HOST` on the network, or if the surrounding system (tool calls to remote APIs, MCP servers, tracing, web fetches) sends data out.

   </details>

5. Name three conditions under which local is the right choice, and one under which it is not even if it is cheaper.

   <details><summary>Answer</summary>

   Simple checkable tasks, high-volume or background work, sensitive data, offline or reproducibility needs, or heavy prompt iteration. Not when a wrong answer is silent or costly and the local model's pass rate is not high enough, since the saving is then paid back in errors and review time.

   </details>
