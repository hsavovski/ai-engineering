# Cost and latency tracking

## Why this matters

An agent run is a loop, and every turn of the loop re-sends the conversation so far. Cost and latency are therefore not properties of "a request" but of a *run*: they grow with the number of turns, the size of tool results, and how much the model thinks. A task that costs a fraction of a cent on a good day can cost a hundred times that when the agent gets stuck in a loop at 2 a.m., and nothing in your tests will tell you unless you measure it.

Two things make this a chapter and not a footnote. First, the numbers you need are already in every API response (token counts) and in the traces you built in [4.7](/part-04-evals-observability/4.7-tracing) (durations), so tracking them is mostly bookkeeping done carefully. Second, careless bookkeeping gives wrong answers that look right: cached tokens counted as full price, thinking tokens missing, the same response summed twice. A number you can't trust is worse than no number, because you'll optimise against it.

You will also meet a decision most hand-written agents skip: what should the agent do when it is *over budget*? Stopping is easy to write and easy to get subtly wrong.

**Learning goals**

- Compute cost per task from usage
- Find latency hotspots in traces
- Set per-task budgets

## Explanation

### From usage to cost

Cost is a sum over model calls of (tokens of each kind) × (price of that kind). Nothing more. The work is in the words "of each kind".

A model call's response carries a **usage** object (glossary: *token usage*). Providers name the fields differently, and the differences are where bugs live. Three families matter for this project:

| Source | Fields you get | Watch out for |
|---|---|---|
| Anthropic Messages API | `input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`; for thinking, `output_tokens_details.thinking_tokens` | `input_tokens` is *not* the whole input (next section) |
| OpenAI-compatible APIs (incl. OpenRouter) | `prompt_tokens` / `completion_tokens`, with `cached_tokens` and `reasoning_tokens` in `*_details` sub-objects; OpenRouter adds a `cost` | field names follow whichever API you call, and OpenRouter's returned `cost` is in credits |
| Ollama (local) | `prompt_eval_count`, `eval_count`, `prompt_eval_cached_count`, plus durations in **nanoseconds** | there is no price: local cost is time (and electricity), not dollars |

Sources: [Anthropic prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) (the three input fields), [Anthropic extended thinking](https://platform.claude.com/docs/en/build-with-claude/extended-thinking) (`thinking_tokens`, reported "of the billed output tokens"), [OpenRouter usage accounting](https://openrouter.ai/docs/guides/guides/usage-accounting) (token counts and cost in credits with every response, reasoning and cached token counts where applicable), [Ollama usage metrics](https://docs.ollama.com/api/usage) (the fields in the table; "All timing values are measured in nanoseconds").

The first design decision, and the one this chapter's practice turns on: **normalise at the edge.** Write one function per provider that maps the provider's usage object to your own record, and let nothing else in the project read provider field names. Something like:

```ts
type Usage = {
  inputFresh: number;   // input tokens billed at the normal input price
  cacheRead: number;    // input tokens read from the provider's cache
  cacheWrite: number;   // input tokens written to the cache this call
  output: number;       // all output tokens, thinking included
  thinking?: number;    // the part of `output` that was reasoning, if reported
};
```

This is a shape, not a solution: deciding which provider field lands in which slot is the exercise.

### Token accounting: cache and thinking

**Cache tokens.** With [prompt caching](/part-02-programming-with-llms/2.7-prompt-caching) the input of one request is split three ways, and Anthropic's docs spell out the identity: `total_input_tokens = cache_read_input_tokens + cache_creation_input_tokens + input_tokens`, where `input_tokens` counts only what comes after the last cache breakpoint ([prompt caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)). If you multiply `input_tokens` by the input price and stop, you will under-count a heavily cached agent by a wide margin, and your "cost per run" will look wonderful. Each of the three slots has its own price: cache writes cost a multiple of the input price (more for the 1-hour lifetime than the 5-minute one) and cache reads a small fraction of it. Those multipliers differ by model and change, so they live on [Landscape](/landscape#anthropic), not here.

Why it matters for agents in particular: the loop re-sends an ever-growing prefix every turn. When the cache works, turn *n* pays the read price for turns 1 to *n*−1 and the full price only for the new tail. When something invalidates the prefix (a timestamp in the system prompt, tool definitions that change order, a compaction that rewrites history), every later turn pays full price again. Tracking `cacheRead / (cacheRead + cacheWrite + inputFresh)` per run, the *cache hit ratio*, is how you notice. A drop in that ratio between two runs of the same task is a bug report.

Other providers report cache reads too, under other names (OpenAI-style `cached_tokens`, Ollama's `prompt_eval_cached_count`), and some have no separate write charge. The `Usage` shape above has the slots; your adapter decides what to put in them.

**Thinking tokens.** Reasoning models produce internal tokens before the visible answer ([1.10](/part-01-how-llms-work/1.10-reasoning-models)). They are billed as output: Anthropic's docs describe `thinking_tokens` as reporting "how many of the billed output tokens were internal reasoning", and when streaming that breakdown "appears only on the final `message_delta` event" ([extended thinking](https://platform.claude.com/docs/en/build-with-claude/extended-thinking); the page marks extended thinking as a legacy feature that Claude 4.7 and later reject, so check which usage fields your model actually returns). Two consequences. Don't add `thinking` to `output` (you would double-count); keep it as a *breakdown* of output. And the visible text can be a tiny fraction of the bill: a short answer after a long think is mostly thinking tokens, and locally the same think shows up as seconds of waiting instead of dollars.

The OpenTelemetry GenAI conventions you used in 4.7 have names for exactly these slots: `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`, `gen_ai.usage.cache_read.input_tokens`, `gen_ai.usage.cache_write.input_tokens` and `gen_ai.usage.reasoning.output_tokens`, the last three marked Recommended "when available and non-zero" ([inference spans](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/client-inference.md); still Status: Development, see 4.7). If your 4.7 spans carry only the first two, this chapter's step is to add the other three, from your normalised `Usage`.

**Other things that get billed.** Tokens are not the only line item. Tool definitions and tool results are input tokens like any others, and server-side tools can add per-use charges on top (web search is billed per search plus the tokens it produces) ([Claude pricing: tool use](https://platform.claude.com/docs/en/about-claude/pricing#tool-use-pricing)). Tokenizers also differ between model generations: Anthropic's pricing page says its newer tokenizer (Claude 4.7 and later) produces approximately 30 percent more tokens for the same text than earlier models, so a tokens-per-character rule of thumb is model-dependent; count with the model's own token-counting endpoint when you need an estimate ([pricing](https://platform.claude.com/docs/en/about-claude/pricing)). For a local model there is no bill, but usage still matters: `prompt_eval_count` growing turn over turn is the local version of a cost curve.

### A worked example

Prices below are **made up** round numbers for arithmetic, not any real model's; take real ones from [Landscape](/landscape). Say input costs $1 per million tokens, output $5, cache reads 0.1× input, cache writes 1.25× input.

A three-turn run where a 10,000-token prefix (system prompt and tool definitions) is cached on turn 1 and each turn adds about 1,000 new tokens:

| Turn | Cache write | Cache read | Fresh input | Output |
|---|---|---|---|---|
| 1 | 10,000 | 0 | 1,000 | 300 |
| 2 | 1,000 | 10,000 | 100 | 200 |
| 3 | 1,000 | 11,000 | 100 | 400 |

Cost = Σ tokens × price ÷ 1,000,000. In units of "tokens at the input price":

- Cache writes: 12,000 × 1.25 = 15,000
- Cache reads: 21,000 × 0.1 = 2,100
- Fresh input: 1,200 × 1 = 1,200
- Output: 900 × 5 = 4,500

Total = 22,800 ÷ 1,000,000 ≈ $0.023. Without caching, the same run sends 11,000 + 11,100 + 12,100 = 34,200 input tokens at full price, plus the same output: 34,200 + 4,500 = 38,700 units, about $0.039. The saving grows with every extra turn, since each adds another read of the whole prefix at a tenth of the price. Do this arithmetic once by hand with real prices from Landscape before you write the function; the function's unit test is this table.

### The price table

The price table is the only part of the cost calculation that goes stale, so isolate it. Keep it as data (a JSON file or a typed constant) keyed by the *exact model id* the API echoes back, with a retrieval date and a source URL per entry. Prices change, and some are promotional ([Landscape](/landscape) says so at the top); a table with no date is a table nobody trusts.

Rules that keep it honest:

- **Unknown model means an explicit failure or a flagged estimate, never a silent zero.** A silent zero is how "we spent nothing" gets reported for a model the table forgot. Local Ollama models are the one legitimate zero: put them in the table as explicit zero-price entries.
- **Some prices depend on the request.** Anthropic's long-context pricing applies per request: "a request over the threshold pays the higher prices even when part of its prompt is a cache hit" ([pricing: long context](https://platform.claude.com/docs/en/about-claude/pricing#long-context-pricing)). If you track a model with tiers, compute the tier per call, not per run.
- **Your number is an estimate.** The Claude Agent SDK says so about its own figure: `total_cost_usd` is a client-side estimate, "not authoritative billing data", computed from a price table bundled at build time, and it can drift when prices change or the installed SDK doesn't recognise a model ([cost tracking](https://code.claude.com/docs/en/agent-sdk/cost-tracking)). Yours has the same limits. Reconcile against the provider dashboard now and then, which is what `costs.md` is for.
- **When the provider reports cost, keep it.** OpenRouter returns a `cost` with every response ([usage accounting](https://openrouter.ai/docs/guides/guides/usage-accounting)); Langfuse takes the same view: when both are available, "ingested costs take priority over inferred ones" ([Langfuse cost tracking](https://langfuse.com/docs/observability/features/token-and-cost-tracking)). Keep your computed figure too: the gap between the two is a useful alarm for a stale table.

### Latency: what to measure

Cost is a sum. Latency is a *shape*: what overlaps, what waits. For a single model call, four numbers matter:

- **Time to first token (TTFT)**: from sending the request to the first streamed token. It is dominated by queueing, loading (locally: loading the model into memory) and **prefill**, processing the whole prompt, which grows with input length. It is what a user perceives as "is it doing anything?".
- **Generation time**: from first token to last. It scales with output tokens, including thinking tokens the user never sees.
- **Tokens per second** = output tokens ÷ generation time.
- **Total latency**: everything, end to end.

The GenAI conventions define these as metrics: `gen_ai.client.inference.duration` is end-to-end ("from when the client issues the inference request to when the response is fully received"), and `gen_ai.client.inference.time_to_first_chunk` is the time to the first chunk of a streaming response, to be reported for streaming calls only ([inference metrics](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/client-inference.md)). You can't measure TTFT unless you stream, which is a reason an agent that "doesn't need streaming" might stream anyway. Locally, Ollama reports the split for you: `load_duration` (model load), `prompt_eval_duration` (prefill) and `eval_duration` (generation) ([Ollama usage](https://docs.ollama.com/api/usage)). That makes "the first call was slow because the model had to load" visible instead of a mystery.

For an *agent run* add two more:

- **Tool time**: the wall-clock duration of each tool call, from your `execute_tool` spans. Shell commands and file reads are usually fast; a test suite or a network call is not.
- **Model time versus tool time**: the share of the run's wall-clock spent in each. This one ratio tells you where to look. If most of the run is model time, the levers are fewer turns, shorter prompts, a faster or smaller model, or less thinking. If most is tool time, the model isn't your problem.

A subtlety: when tools run one after another, run time is roughly the sum of model and tool durations, but once you parallelise tool calls or run sub-agents ([3.10](/part-03-agents/3.10-multi-agent)) the spans overlap and the sum overstates. Take the run's duration from the root span, and treat per-kind sums as *work*, not elapsed time.

A made-up run as a timeline, one column per second:

```text
second:        0         1         2
               012345678901234567890
chat turn 1    ██████
read_file            █
chat turn 2           ███
run_shell                ████████      <- the tests
chat turn 3                      ███
```

In this run, model time is 12 s of 21 s, and the single widest span is a tool, the test suite. No amount of prompt tuning fixes that. Without the timeline you would have blamed the model.

### Finding hotspots in a trace

You already have the data from 4.7. A routine for a slow or expensive run, in order:

1. **Per-run totals first.** Total duration, total cost, number of turns, model time share, cache hit ratio. Five numbers tell you which kind of problem you have.
2. **Widest span.** Is it one slow call or many small ones? One slow model call: check its input tokens (prefill) and output tokens (thinking?). One slow tool: fix the tool.
3. **Cost per turn.** Look at input tokens per turn. A line that climbs steeply is context creep ([3.4](/part-03-agents/3.4-context-engineering)): a large tool result is being carried along, and re-billed, every turn after.
4. **Repeats.** The same tool with the same arguments three times is a loop, and each repeat costs a full turn.
5. **Compare two runs of one task**, ideally on different models. Cost and latency belong in the same table as the pass rate from [4.3](/part-04-evals-observability/4.3-code-based-checks), because "cheaper but fails more often" is only visible when both are on one row, and the honest unit is **cost per successful task**: total spend divided by the number of runs that passed. A model with half the price and half the pass rate costs the same per success.

Langfuse does the aggregation for you in its UI once usage is on the generation spans: it records usage and cost per usage type on each generation, infers cost from the model name against a price definition if you don't send one, and lets you slice cost by model, user or tag ([Langfuse cost tracking](https://langfuse.com/docs/observability/features/token-and-cost-tracking)). That's convenient, and it is also a second price table you now have to keep right; the model-name match is the first thing to check when a number looks wrong.

One trap carried over from 4.7: summing token counts across spans can **double-count** when more than one layer reports the same request (for instance an instrumented SDK inside your own instrumented loop). Pick one source of truth per request; with a hand-written loop that is the span your own adapter writes.

### Budgets and alerts

A **budget** is a limit the program enforces; an **alert** is a signal a person gets. They answer different questions and you want both, at different scales.

**Per-run budgets (a guard in the loop).** Before each model call, check whether the run is already over its limit; after each call, add the call's cost to the running total. Design points, each from a real failure mode:

- **What you can limit.** Dollars is the most natural, but it needs a price table; tokens, turns and wall-clock time need none, and a *local* model has no dollars at all, only time and tokens. A robust guard supports a limit per dimension and trips on whichever comes first. You already have a turn limit from 3.2: a cost budget is its sibling, not a replacement.
- **Check before the call, not only after.** An overrun is detected only after the response has arrived and been paid for. The Agent SDK's `maxBudgetUsd` is documented the same way: it stops the query when the client-side cost estimate reaches the value, and "the estimate can pass this value, so leave headroom" ([TypeScript SDK reference](https://code.claude.com/docs/en/agent-sdk/typescript)). To do better, estimate the next call's minimum cost from the current input size (known before you send) and refuse the call if it alone would break the limit.
- **Stopping is a result, not a crash.** The run should end with an explicit status (`budget_exceeded`) and whatever it produced so far, including its cost, and the eval runner from 4.3 should score it as a failure rather than a missing row. The Agent SDK does this: a run that crosses its budget ends with an `error_max_budget_usd` result that still carries cost ([cost tracking: failed conversations](https://code.claude.com/docs/en/agent-sdk/cost-tracking)).
- **Count what you spent on failures.** The same page warns that a conversation which fails midway still consumed tokens, and that some error results report less usage than was spent. Add each call's cost *as it happens*, not at the end of a successful run, so a crash can't erase the spend.
- **Parallel work shares one meter.** Sub-agents and parallel tool calls must charge the same running total, or a "per-run" budget quietly becomes a per-agent one.
- **Streaming complicates it.** Output tokens aren't final until the response ends (the Agent SDK page notes the real output count arrives at the end of the response), so a mid-stream guard can only cut on an estimate, and cutting wastes the work already generated.

**Per-task and per-suite budgets.** A single hard limit is blunt. A better scheme gives each *task type* a budget derived from measurement: run it ten times, look at the distribution, set the limit at a comfortable multiple of the median, and treat a run that hits it as a finding (the agent is lost, or the limit is too tight) rather than noise. For the eval suite, the cost cap in the 4.6 CI step is the same idea one level up: cap the *whole run*, and stop starting new cases when it is reached.

**Alerts** are for what a single run can't tell you: the *distribution* moving. Useful ones are cheap to compute from per-run records: median cost per task rising between two commits, cache hit ratio falling, p95 latency up, tool errors up. The trap is alerting on a *total* ("we spent $5 today") when the cause is a *rate* (this task now costs three times what it did last week). Compare like with like: the same task set, the same model.

One limit lives outside your code: provider-side spend limits and credit balances. Use a separate key for experiments and keep its credit balance small. Your own guard is the first line of defence and is only as good as your price table; the provider's limit holds when your code has a bug.

## Practice

**Brief:** Add cost per run to `project/` (computed from usage and a price table) and a `--budget` flag that stops the agent when exceeded. Log real spend in `costs.md`. You write all the code; no solution is provided.

**Where:** A step in the growing `project/` (see `project/ROADMAP.md`, step 18). It builds on the tracing from 4.7 (step 17) and, through it, the agent loop from 3.2.

**Steps**

1. **Collect real usage objects first.** Make one call on each of: a paid model with caching in play (two requests with the same long prefix), a paid reasoning model, and local Qwen. Save the raw `usage` JSON from each in `notes/cost-latency.md`. Note which field holds each of: fresh input, cache read, cache write, output, thinking. Write "not reported" where a provider doesn't say.
2. **Define your `Usage` record and one adapter per provider.** Nothing outside the adapters reads provider field names. Unit-test each adapter against the JSON you saved, including a thinking response and a cached response.
3. **Write the price table as data.** Entries keyed by exact model id, each with prices per category, a source URL and a retrieval date. Take prices from [Landscape](/landscape) or the provider page itself, never from memory. Include Ollama models as explicit zero-price entries. Decide and test what happens for an unknown model.
4. **Write `cost(usage, model)`** as a pure function and test it against the worked example above (the three-turn table, with real prices you looked up). Add cases for: no cache; cache read only; thinking counted once, not twice.
5. **Meter every model call.** The loop adds each call's cost to a running total as it happens. Put the usage numbers on each model-call span (`gen_ai.usage.*` names, in your attribute module from 4.7) and the computed cost under a clearly marked custom attribute of your own: check the spec page for whether a standard attribute for dollar cost exists before you invent one.
6. **Print a run summary** at the end: turns, total input (fresh / cache read / cache write), output (with thinking), cost, wall-clock, model time versus tool time, cache hit ratio. Persist the same record per run (next to the step log), so you can aggregate runs later.
7. **Add `--budget`.** Accept `--budget <usd>`, plus a way to limit tokens or time so local runs (price zero) can be bounded too. Check before each model call; end the run with a distinct status, the partial result and the cost, not an exception stack. Choose and write down your policy for the call that crosses the line (refuse it up front on an estimate, or allow it and stop after).
8. **Provoke it.** Give the agent a task it can't finish (an impossible edit, a question about a file that doesn't exist) with a tiny budget. Confirm it stops, reports `budget_exceeded`, and that the final cost in the summary equals the sum of the model-call costs in Langfuse.
9. **Find a hotspot.** Run one task of 10 or more steps on local Qwen and on one paid model. In the traces, find the widest span and the turn where input tokens jump. Write in `notes/cost-latency.md`: model-time share, cache hit ratio, which turn grew the context, and one change you would make because of it. If you make it, re-run and record the before and after.
10. **Reconcile and log.** Add a row to `costs.md` for each paid run (provider, tokens in and out, cost, whether the figure is the provider's or your estimate) and update the total. Compare your computed figure to the provider dashboard or the `cost` OpenRouter returned for at least one run, and note the difference and its likely cause.

**Done when**

- A run prints a summary with cost and latency breakdowns, and the persisted per-run record has the same numbers.
- Cache reads, cache writes and thinking tokens each have their own slot in your `Usage` record, and a test shows that a cached response is *not* priced as if all its input were fresh.
- The price table is data with a source and a date per entry; an unknown model fails loudly or is flagged as an estimate, and no code path produces a silent zero for a paid model.
- `--budget` stops a run that cannot finish with a distinct, recorded status, and the recorded cost includes the call that crossed the line.
- In Langfuse, model-call spans show usage including cache and thinking tokens where the provider reports them, and the span costs add up to the run total.
- `notes/cost-latency.md` records the hotspot you found and what you changed (or would change); `costs.md` has a row for every paid run you made, and your computed cost was compared against the provider's at least once.

## Check questions

1. A call to a Claude model reports `input_tokens: 150`, `cache_read_input_tokens: 40000`, `cache_creation_input_tokens: 0`. A teammate's script reports the input cost of this call as "essentially nothing". What did the script do wrong, and what is the call's total input?

   <details><summary>Answer</summary>

   It priced only `input_tokens`, which counts just the tokens after the last cache breakpoint. Total input is `cache_read_input_tokens + cache_creation_input_tokens + input_tokens`, here 40,150 tokens. The 40,000 cache-read tokens are billed at the cache-read price, a fraction of the input price but not zero, so the cost is small but not nothing, and the script has to price each of the three categories separately.

   </details>

2. Your agent's cost per run doubles after a change that only reordered the tool definitions in the system prompt. Output tokens are unchanged. What is the most likely cause, and which number would have shown it?

   <details><summary>Answer</summary>

   Reordering the tool definitions changed the prompt prefix, so the cache no longer matched: tokens that were cache reads became cache writes (priced higher) or fresh input on every turn. The cache hit ratio, `cacheRead / (cacheRead + cacheWrite + inputFresh)`, would have dropped sharply between the two runs, with total input roughly constant but split into different categories.

   </details>

3. A trace shows a 40-second run: 12 seconds in model calls and 25 seconds in a single `run_shell` span. A colleague proposes switching to a faster model. What do you say, and what do you check?

   <details><summary>Answer</summary>

   A faster model attacks at most the 12 seconds of model time; the biggest share is the tool. Look at what that shell command does (a full test suite, a network call, a missing cache) and fix or bound it (narrower tests, a timeout). Also check where the remaining 3 seconds went, and whether spans overlap: if tools or sub-agents run in parallel, durations don't add up to elapsed time, so take the run's duration from the root span.

   </details>

4. Your `--budget 0.50` guard checks the running total after each model response. A run ends having spent $0.71. Is this a bug? Name two ways to tighten it and one thing that stays unfixable.

   <details><summary>Answer</summary>

   Not necessarily a bug: a check after the response can only stop the run once the call that crossed the limit has been paid for, which is the behaviour (and the "leave headroom" warning) of the Agent SDK's `maxBudgetUsd`. To tighten it: estimate the next call's minimum cost from the current input size and refuse the call before sending if it would exceed the budget; and lower `max_tokens` (or the thinking budget) as the remaining budget shrinks, so a single call can't be large. What remains is that output length and thinking are unknown until generation finishes, so a single call can still overshoot, and a streaming guard that cuts early works only from estimates and throws away work.

   </details>

5. Model A is 40% cheaper per run than model B on your eval set, but passes 55% of cases against B's 90%. Which is cheaper in practice, and what figure do you report?

   <details><summary>Answer</summary>

   Report **cost per successful task**: total spend divided by the number of passing runs, not cost per run. With A at 0.6 of B's per-run cost, A's cost per success is 0.6 / 0.55, about 1.09 times B's per-run cost, versus 1 / 0.90, about 1.11, for B: nearly the same, and A also leaves 45% of tasks unsolved, which in practice means reruns or human time. Cost belongs in the same table as the pass rate; either number alone is misleading.

   </details>
