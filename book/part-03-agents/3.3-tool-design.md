# Tool design

## Why this matters

In [3.2](/part-03-agents/3.2-agent-loop) you wrote the loop, and the loop turned out to be about thirty lines. Everything the agent can actually *do* sits behind the tools, and that is where agents succeed or fail in practice. A model that picks the wrong tool, passes a malformed path, or drowns in a 40,000-token result has not failed at reasoning. It has been handed a bad interface.

Tools for models are not APIs for programmers. A programmer reads the docs once, remembers them and calls the function the same way every time. A model sees the name, description and schema afresh on every request, guesses at the parts you left implicit, and has a limited context to spend on your output. Anthropic's engineering team frames a tool as a contract between deterministic software and a non-deterministic agent, and argues that tools should therefore be designed for agents rather than written like functions for developers ([Writing effective tools for agents](https://www.anthropic.com/research/writing-tools-for-agents)). This chapter is about writing that contract well, and about finding out whether you did by watching an agent use it.

**Learning goals**

- Design tool names, descriptions, inputs and outputs for a model
- Return errors and results that help the model recover
- Evaluate tools by watching the agent use them

## Explanation

### A tool is a contract with a caller who guesses

When you call a function in TypeScript, the compiler enforces the contract. When a model calls a tool, three things are different:

1. **The caller reads, it doesn't know.** All it has is the tool's `name`, `description` and `input_schema` (a JSON Schema, see [2.5](/part-02-programming-with-llms/2.5-structured-output)), which Claude's API folds into the prompt. Anthropic's tool-definition docs call the description "by far the most important factor in tool performance" and ask for what the tool does, when to use it and when not to, what each parameter means, and caveats such as what it does *not* return ([Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools), "Best practices").
2. **The caller is non-deterministic.** The same prompt may produce a different call on the next run, and a weaker model (your local `qwen3:8b`, say) will make mistakes a stronger one doesn't. A design that only works when the caller is careful is fragile.
3. **The result is the caller's next input.** What you return is not a return value, it is text that lands in the context window and steers the next step ([3.2](/part-03-agents/3.2-agent-loop#tool-failures-are-inputs-to-the-next-turn)).

So there are four surfaces to design, and they all matter: the **name**, the **description**, the **input schema**, and the **output** (including errors). A useful test for the lot: if a new colleague who had never seen your codebase could not tell from the definition alone when to call the tool and what to pass, a model can't either. The engineering post suggests the same framing: describe the tool as you would to a new hire, making implicit context explicit ([Writing effective tools](https://www.anthropic.com/research/writing-tools-for-agents)).

Anthropic's earlier agents guide calls this the **agent-computer interface (ACI)** and says to "plan to invest just as much effort in creating good agent-computer interfaces (ACI)" as in human-computer interfaces, in its appendix on prompt-engineering your tools ([Building effective agents](https://www.anthropic.com/engineering/building-effective-agents), Appendix 2). The same appendix offers the principle I'd keep above all others: "Poka-yoke your tools. Change the arguments so that it is harder to make mistakes." Its example: during their SWE-bench work the model made mistakes with relative paths once the agent had left the root directory, so they "changed the tool to always require absolute filepaths". Poka-yoke is the manufacturing term for mistake-proofing: don't write a warning that says "be careful", change the design so the mistake is hard to make.

### Choosing granularity

The first design decision is which tools exist. Two instincts pull in opposite directions:

- **One tool per API endpoint.** Easy to write, mirrors the backend. The article warns that "more tools don't always lead to better outcomes", and that wrapping existing API endpoints one for one is a common mistake.
- **One tool that does everything** (`do(action, args)`). Easy to count, but the schema becomes a pile of optional fields and the model has to learn a mini-language.

The guidance from Anthropic's docs and engineering post lands in the middle: tools should match the *workflows the agent actually performs*, not the shape of your internals. Their examples: a `schedule_event` that finds availability and creates the event, instead of separate list and create calls; a `search_logs` that returns the relevant lines, instead of a `read_logs` that returns everything; a `get_customer_context` instead of several getters ([Writing effective tools](https://www.anthropic.com/research/writing-tools-for-agents)). The docs make the same point at the other end of the scale: group `create_pr`, `review_pr` and `merge_pr` into one tool with an `action` parameter, because fewer, more capable tools "reduce selection ambiguity" ([Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)).

Notice the two sources don't draw the line in the same place. That is the real lesson: there is no universal granularity. Use these questions to decide:

| Question | If yes |
|---|---|
| Does the agent almost always call A and then B, passing A's result unchanged? | Merge them. Every extra call is a turn, some context and a chance to go wrong. |
| Would the tool dump data the agent mostly doesn't need (`list_all_contacts`)? | Replace it with a narrower one (`search_contacts(query)`) so the agent asks for what it needs. |
| Do two tools have overlapping purposes, so *you* couldn't say which to use? | Merge them or sharpen their descriptions. If you can't choose, the model can't. |
| Does one tool have unrelated modes with different failure behaviour and different risk (read vs delete)? | Split it. Risk differences also matter for permission prompts later ([5.4](/part-05-harnesses/5.4-mini-harness)). |
| Is the tool's name or description growing a long "or" list? | It is probably two tools. |

A reference point is the tool Anthropic ships for file editing: a single `str_replace_based_edit_tool` with `view`, `str_replace`, `create` and `insert` commands, where `str_replace` takes an `old_str` that must match "exactly, including whitespace and indentation" ([Text editor tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/text-editor-tool)). Four operations on one resource, grouped. Your practice splits `edit_file`, `list_files` and `search` into separate tools, and that is a choice you can later revisit with evidence.

### Naming and namespacing

Names are the first thing the model sees, and in a list of many tools they are most of what it reads. Rules that hold up:

- **Verb plus object, concrete and consistent.** `search_files`, `read_file`, `edit_file`: one pattern, so the model can predict a name it hasn't seen. Avoid `process`, `handle`, `run_task`.
- **Parameter names are part of the name.** `user_id` instead of `user`. The engineering post recommends unambiguous parameter names for this reason.
- **Namespace when tools come from several places.** Group by service or resource with a common prefix, as in `asana_search` and `jira_search` ([Writing effective tools](https://www.anthropic.com/research/writing-tools-for-agents)), or `github_list_prs` and `slack_send_message` ([Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)). With one small agent you barely need it. It matters the moment you attach MCP servers ([3.6](/part-03-agents/3.6-mcp-using)): two servers can both offer a `search`, and the model can't tell them apart by luck.
- **Prefix or suffix: test it.** The post reports that choosing between prefix and suffix namespacing had "non-trivial effects" on tool-use evaluations and varies by model. Take that as an instruction to measure your scheme, not a recommendation of either.
- **Names have a syntax.** On Claude's API a name must match `^[a-zA-Z0-9_-]{1,128}$` ([Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)). Other providers have their own limits, so lowercase snake case keeps you out of trouble.

### Descriptions and schemas: write for the guesser

A weak definition, and a better one for the same tool (both made up for this chapter, not from the sources):

```json
{ "name": "search", "description": "Search files.",
  "input_schema": { "type": "object", "properties": { "q": { "type": "string" } } } }
```

```json
{
  "name": "search_files",
  "description": "Search the text of files under the project directory for a regular expression and return matching lines with their file path and line number, at most `max_results` of them. Use it to find where something is defined or used when you don't know which file. Use list_files instead to see which files exist, and read_file once you know the file. It searches contents, not file names. Skips .git and node_modules. If there are more matches than max_results the result says so: narrow the pattern or the directory rather than raising max_results.",
  "input_schema": {
    "type": "object",
    "properties": {
      "pattern": { "type": "string", "description": "Regular expression (JavaScript syntax), matched against each line. Case-sensitive." },
      "directory": { "type": "string", "description": "Directory to search, relative to the project root. Defaults to the whole project." },
      "max_results": { "type": "integer", "description": "Default 20, maximum 100." }
    },
    "required": ["pattern"]
  }
}
```

What the second one does that the first doesn't, as a reusable checklist:

- Says **what the tool does and doesn't do** ("contents, not file names"), and points to the sibling tools for neighbouring jobs. Overlap between tools is the commonest source of wrong picks.
- Says **what comes back**, so the model can plan around it.
- Gives **parameter meaning and format** (regex flavour, relative to what, defaults and limits).
- **Steers behaviour at the limit** ("narrow the pattern"). The post makes this point about truncation: steer the agent towards efficient strategies, such as several small targeted searches instead of one broad one.
- Uses **`enum`, `required` and bounds** so invalid calls are impossible or obvious. That is poka-yoke in schema form. (If you validate with Zod, per [2.5](/part-02-programming-with-llms/2.5-structured-output), the same schema is your runtime check.)

The docs add `input_examples`: example inputs, validated against the schema, that show the model what well-formed calls look like. They suit nested or format-sensitive inputs, and the docs put their cost at roughly 20 to 50 tokens for a simple example and 100 to 200 for a nested one, with descriptions still the priority ([Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools), "Providing tool use examples"). One more rule from the same page: if a parameter asks the model why it is making the call, ask for a short explanation, because asking for its step-by-step reasoning "might lead to a `reasoning_extraction` refusal".

How much does the wording matter? The engineering post says precise description refinements mattered a great deal in their own work, citing a Claude Sonnet 3.5 result on SWE-bench Verified, and a web-search tool where Claude kept appending "2025" to queries until the description was fixed. Treat those as anecdotes from the authors' evaluations, not a law. The portable point is that descriptions are cheap to change and their effect is measurable, so iterate on them with a test, not by feel.

### Outputs: high signal, few tokens

The result is where most designs go wrong, in the opposite direction from the description: they return too much. Whatever you return is paid for on this turn and, as you saw in 3.2, on every later turn because the history is re-sent.

**Return what the next decision needs.** The engineering post advises high-signal fields (a name, a file type) over low-level technical identifiers (UUIDs, MIME types), and reports that resolving cryptic alphanumeric IDs to something semantic, or even to a simple 0-indexed id, reduced hallucinations and improved retrieval precision. The reason is mechanical: a model copying `a3f9-77e1-...` has to reproduce it character for character, and one wrong character becomes a "not found" a few turns later. If the agent needs an id for a follow-up call, keep it, but put the readable part first.

**Offer a size knob.** The same post describes a `response_format` enum with `concise` and `detailed` values, with an example where the detailed response took 206 tokens and the concise one 72, about a third. The detailed one carried the ids that follow-up tools needed. You can borrow the idea without the enum: a `limit`, a `fields` list or a line range does the same job. Anthropic's text editor tool has a `view_range` for the same reason, and an optional `max_characters` that truncates what a view returns ([Text editor tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/text-editor-tool)).

**Paginate, filter, truncate, with defaults.** Anthropic's post says Claude Code restricts tool responses to 25,000 tokens by default. That figure is Claude Code's own and says nothing about your agent, but notice the shape: a hard ceiling that exists even though no single tool is *meant* to hit it. Where you cut, say so in the output, and say how to get more:

```text
[Showing 20 of 143 matches for "retry". Narrow the pattern or search a subdirectory
 (for example directory: "src/net") to see the rest.]
```

A silent cut is worse than an overflow: the model believes it saw everything. The truncation marker from the 3.2 practice should now carry a hint, not just a notice.

**Pick a format the model reads well.** The post says response structure (XML, JSON, Markdown) can affect performance and the right choice depends on the task and model, so evaluate it. The agents guide's advice on tool formats is a good default: "Keep the format close to what the model has seen naturally occurring in text on the internet" ([Building effective agents](https://www.anthropic.com/engineering/building-effective-agents), Appendix 2). Compare `grep -n` style output (`src/a.ts:12: const x`) with an array of objects with four keys per match. The first is shorter, and models have seen it countless times.

### Errors that help the model recover

3.2 gave the rule: errors are results, not exceptions. The design question now is what the error says. An error is the one moment the model is guaranteed to read your text carefully, because its goal is blocked. Use it.

| Failure | Unhelpful | Helpful |
|---|---|---|
| Missing file | `ENOENT: no such file or directory` | `File not found: src/util.ts. Files in src/: index.ts, utils.ts, net/. Did you mean src/utils.ts?` |
| Edit text not found | `Error: no match` | `old_text was not found in src/utils.ts. The text must match exactly, including indentation. Nearest line: 41: "  const retries = 3". Read the file around line 41 and retry.` |
| Edit text matches several places | `Error` | `old_text matches 3 places (lines 12, 40, 77). Add surrounding lines to make it unique.` |
| Invalid argument | `ValidationError: Expected number, received string` | `max_results must be an integer between 1 and 100, got "lots".` |
| Too much output | (silently cut off) | the truncation marker above |
| Empty result | `[]` | `No matches for "retries" in src/. Search is case-sensitive; try a different spelling or directory.` |

Three habits behind the right-hand column: say **what happened**, say **what was valid or nearby** (a listing, the closest match, the allowed range), and say **what to do next**. Anthropic's post makes the same point in its token-efficiency section: error responses should be actionable rather than opaque error codes or tracebacks. An empty result is the quiet cousin of an error: `[]` doesn't say whether the thing doesn't exist or the query was wrong.

Two cautions. First, an error message is text that goes into the model's context, so don't put secrets, internal stack traces or raw third-party responses in it. Second, a helpful message can steer a model somewhere you didn't intend if it names a dangerous alternative: "try with sudo" would be a bad suggestion.

For the edit tool specifically, the failure modes teach a design lesson. An exact-match replacement (the `str_replace` shape) is safer than line-number edits, because line numbers shift after every edit and a model that edits twice in a row can easily edit the wrong line the second time. The price is that the model must reproduce the old text exactly, and that is where the "no match" and "matches several places" errors above come from. Which trade you choose, and what your tool says when it fails, is yours to decide and defend in the practice.

### Testing tools with the agent itself

You can't judge a tool definition by reading it. Whether it works is an empirical property of a particular model reading it in a particular context, so the way to test tools is to run an agent on realistic tasks and look at what it did. Anthropic's post describes the workflow in three steps, and it scales down to a one-person study project:

1. **Prototype.** Write the tools quickly and run them with an agent (a local MCP server in Claude Code is their route; your own loop from 3.2 is yours).
2. **Evaluate.** Write realistic tasks with a checkable outcome: not toy tasks, but ones that need several tool calls and could go wrong in several ways. Run them and record more than pass or fail: the post lists accuracy, total runtime, number of tool calls, token consumption and tool errors. Your 3.2 step log already has those fields. It also warns against over-strict verifiers that reject a correct answer over formatting differences.
3. **Read the transcripts.** The reasons for failures are in the transcripts, not in the aggregate. Look for places where the agent got stuck or confused, and for patterns across runs.

What to look for when you read a transcript, and what it usually means:

| In the transcript | Usually means |
|---|---|
| Many calls to a tool, with small variations | The description doesn't make a parameter's format clear, or the result doesn't answer the question. |
| A tool never used when it should be | Its name or description doesn't match how the task is phrased, or another tool overlaps. |
| The wrong tool, then the right one | Overlap, or a missing "use X instead for Y". |
| Invalid arguments | Schema too loose, or the description is missing a format. Tighten it or add an example. |
| The same file read twice | The output was truncated without telling the model, or the model lost track of it. |
| Retry after an error without changing anything | The error didn't say what to change. |
| The agent describes a plan the tools can't carry out | A capability you assumed exists doesn't. Consider adding a tool. |
| A long result followed by a wrong answer | Too much noise. Cut the output. |

The table is my reading of common patterns, not a list from the sources. Check it against your own transcripts.

The post also notes that the analysis can itself be delegated: paste the evaluation transcripts into Claude Code and ask it to analyse them and refactor the tools. Its authors say most of the advice in the post came from repeatedly optimizing their internal tools this way. They use held-out test sets so the tools aren't tuned only to the examples they were designed around. For a study project with three tasks, the held-out idea means: after redesigning a tool because of task 2, re-run tasks 1 and 3 and one *new* task, to see that you didn't just fix the transcript in front of you.

Two caveats of my own. The model you test with matters: a tool that a strong paid model uses flawlessly may confuse `qwen3:8b`, and a design that survives the weaker model is usually better for both. And three runs show a kind of failure, not a rate; [Part 4](/part-04-evals-observability/4.1-error-analysis) is about turning that into measurement.

## Practice

**Brief:** Add `edit_file`, `list_files` and `search` tools to `project/`, following the article. Run 3 tasks, read the transcripts, and redesign at least one tool based on what the agent got wrong.

**Where:** a step in the growing `project/` (see `project/ROADMAP.md`, step 2). It builds on step 1 from [3.2](/part-03-agents/3.2-agent-loop): the same loop and step log. The notes go in `notes/tool-design.md`. You write all the code; I haven't provided any.

**Steps:**

1. **Design on paper first.** In `notes/tool-design.md`, before writing code, write for each of the three tools: name, description (as the model will read it), input schema, and what the output looks like on success and on each failure you can think of. For `edit_file`, decide which edit style you use (exact text replacement, line ranges, or whole-file write) and write down why. Decide the caps for `list_files` and `search`, and what they print when exceeded.
2. **Predict.** Pick three tasks in a scratch repo (a copy of a small project, or a copy of this repo's `scripts/` folder) that need the new tools. For example: "find where X is configured and change its value", "rename a function used in several files", "add a missing check to a function and say which file it is in". Write what you expect the agent to get wrong with each tool.
3. **Implement the tools** with validated arguments (reuse your 3.2 validation and errors-as-results handling). Every failure returns a message in the style of the table above. Keep all paths inside the scratch directory: reject anything that resolves outside it, because models do write `../`.
4. **Register them** in the loop next to `read_file` and `run_shell`. Decide whether `read_file` and `run_shell` should stay. Removing a tool the new ones replace is a design decision too, and you can test it.
5. **Run the three tasks** on a local model, and keep each run's JSONL log. Don't coach the agent in the prompt between runs.
6. **Read the transcripts** and annotate in your notes, per run: each call that was wasted, wrong or malformed; what the agent had seen just before it went wrong; and which tool surface (name, description, schema, output, error) is responsible. Use the transcript-reading table above.
7. **Redesign at least one tool** based on a specific failure in a transcript: change the description, schema, output or error, and record the before and after text. Re-run the failed task and one other. Say whether it helped, and whether the change helped or hurt the other task.
8. **Try one paid model** (a cheap one from [Landscape](/landscape); a handful of runs, record the spend in `costs.md`) on the same three tasks and note one place where its use of the tools differs.
9. **Write down** what you'd change about the tool design if you could change only one thing, and what you'd test next. Commit.

**Done when:**

- The three tools exist in `project/`, the loop uses them, and none of them throws into the loop: failures come back as messages.
- Each of the three tasks has a saved log, and `notes/tool-design.md` has an annotation per run that names concrete calls (by turn number) where the agent was wrong or wasted effort.
- At least one tool was changed because of what a transcript showed, with its before and after definition in the notes and a re-run showing the effect (better, worse or no change are all valid findings if reported honestly).
- A path that escapes the scratch directory, a search with more results than your cap, and an edit whose target text is missing each return a message you've read and judged sufficient for a model to recover from.
- No tool output in your logs exceeds your cap, and each truncation tells the model how to get more.

## Check questions

1. Why is a tool definition "a contract with a non-deterministic caller", and what does that imply for how much you rely on the model being careful?

   <details><summary>Answer</summary>

   The model only sees the name, description and schema, guesses at anything you left implicit, and may behave differently from run to run and across models. So correctness should come from the design, not from care: make mistakes hard (an enum, a required field, absolute paths, a bounded integer: "poka-yoke"), say in the description what the tool does and doesn't do, and make errors tell the model how to correct itself.

   </details>

2. Your agent has `list_users`, `list_events` and `create_event`, and for "schedule a meeting with Dana on Tuesday" it uses all three and sometimes picks the wrong user. What would you try, and what would you check before and after?

   <details><summary>Answer</summary>

   Consider consolidating into one workflow-shaped tool (a `schedule_event` that resolves the attendee and checks availability), or at least turn `list_users` into a narrower `search_users(name)` that returns readable names with the id attached. Before changing anything, read transcripts for the actual failure (wrong match? too many users returned? ids copied wrongly?) and record accuracy, calls and tokens on a few tasks. Afterwards re-run the same tasks plus a held-out one. A granularity change is a hypothesis, and the evaluation decides.

   </details>

3. A `search` tool returns up to 500 matching lines. Describe two problems this causes and a better design.

   <details><summary>Answer</summary>

   It costs tokens on this turn and on every later turn, because the history is re-sent, and the model has to find the few relevant lines in a lot of noise, which can make its next step worse. A better design caps results with a sensible default, lets the model narrow by directory or pattern, and when it cuts the output says how many matches exist and how to narrow, so the model never believes a truncated list is complete.

   </details>

4. Rewrite this error into one the model can act on: `Error: edit failed`.

   <details><summary>Answer</summary>

   Say what happened, what was valid or nearby, and what to do: for example, "old_text was not found in src/utils.ts (the text must match exactly, including indentation). The closest line is 41: `  const retries = 3`. Read lines 35 to 45 and retry with the exact text." If it matched several places, say how many and where, and ask for more surrounding lines. Any version that includes the three parts is fine.

   </details>

5. After redesigning a tool so that task 2 passes, how do you know you haven't made things worse, and what does the Anthropic article recommend to avoid overfitting?

   <details><summary>Answer</summary>

   Re-run the other tasks and at least one new one that you did not use while designing. The article recommends held-out test sets so the tools are not tuned only to the tasks they were developed against. With a handful of runs you can only see kinds of failure, not rates, so treat a pass as weak evidence and look at the transcripts, not just the result.

   </details>
