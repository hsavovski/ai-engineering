# Build the agent loop from scratch

## Why this matters

Every agent, from Claude Code to a customer-support bot, is the same small loop around tool calls. Writing it yourself removes the magic and gives you the project you'll grow through the rest of the book: nearly everything in Parts 3 to 5 is something you bolt onto this loop (better tools, context management, tracing, permissions), and when an agent misbehaves, you debug the loop.

[3.1](/part-03-agents/3.1-workflows-vs-agents) defined an agent as an LLM that, in a loop, chooses which tool to call next until it decides the goal is met or a limit stops it. [2.6](/part-02-programming-with-llms/2.6-tool-calling) showed one tool round trip by hand. This chapter is the second thing placed inside a `while`. It is short on theory on purpose: the loop is about thirty lines. What takes the time is everything around it, and that is where local and paid models start to differ.

**Learning goals**

- Implement the agent loop with no framework
- Handle stop conditions, errors and max turns
- Observe how local and paid models differ in the loop

## Explanation

### The loop

Anthropic's tool-use docs describe it as "a `while` loop keyed on `stop_reason`": send a request with your tools, run whatever tools the reply asks for, send the results back, and "repeat ... while `stop_reason` is `"tool_use"`" ([How tool use works](https://platform.claude.com/docs/en/agents-and-tools/tool-use/how-tool-use-works)). The Agent SDK docs describe Claude Code's own loop the same way: Claude evaluates the prompt, calls tools, receives the results "and repeats until the task is complete" ([How the agent loop works](https://code.claude.com/docs/en/agent-sdk/agent-loop)).

```mermaid
flowchart TD
  start([user goal]) --> msgs[messages = system + user goal]
  msgs --> call[call the model with messages + tool definitions]
  call --> append[append the assistant message to messages]
  append --> q{tool calls in the reply?}
  q -->|no| done([final answer: stop])
  q -->|yes| run[run each tool, catching errors]
  run --> res[append one result per call to messages]
  res --> lim{turn limit or budget hit?}
  lim -->|no| call
  lim -->|yes| halt([stop: limit reached])
```

Read the diagram as code, in this order:

1. **Call.** Send `messages` and the tool definitions to the model.
2. **Append the reply.** The whole assistant message goes into `messages`, tool-call blocks included. Skipping this is the classic bug: the next request then contains a tool result for a call the model never "made", which providers reject.
3. **Branch.** No tool calls: the model has answered, and the loop is over. Tool calls: continue.
4. **Execute.** Run each requested tool. Your code does this, not the model ([2.6](/part-02-programming-with-llms/2.6-tool-calling)).
5. **Append the results.** One result per call, matched to it (by `id` on Claude and OpenAI-style APIs, by tool name on Ollama's native API, as the 2.6 comparison table showed).
6. **Check your limits, then repeat.**

The shape of a loop in TypeScript, with the provider-specific parts left as named gaps. `callModel`, `runTool`, `logStep` and the limits are what you write:

```ts
const messages: Message[] = [system(prompt), user(goal)]

for (let turn = 1; turn <= MAX_TURNS; turn++) {
  const reply = await callModel(messages, tools)   // 1. one HTTP call
  messages.push(reply.message)                     // 2. the model's turn, tool calls included
  logStep({ turn, reply })

  if (reply.toolCalls.length === 0) return reply.text   // 3. no tool call: done

  for (const call of reply.toolCalls) {            // 4-5. execute and answer every call
    const result = await runTool(call)             //      (never throws: errors become results)
    messages.push(toolResultMessage(call, result))
    logStep({ turn, call, result })
  }
}
throw new Error('stopped: MAX_TURNS reached')      // 6. the limit is yours
```

Nothing in it is agent-specific except that the `for` is driven by what the model says. Everything in the rest of the chapter hangs off the six numbered lines.

### The message list is the state

The loop has no memory besides `messages`. Each request is stateless: the API sees the entire array again, so the model "remembers" step 1 at step 7 only because step 1 is still in the array. Consequences worth internalising early:

- **The run is its transcript.** To resume a run, save `messages`. To debug one, read `messages`. To test a change to your system prompt, replay the same `messages` against it. Claude Code's session IDs and resume feature are this idea with a file behind it ([How the agent loop works](https://code.claude.com/docs/en/agent-sdk/agent-loop), "Sessions and continuity").
- **It only grows.** Per the Agent SDK docs, the context "does not reset between turns within a session. Everything accumulates: the system prompt, tool definitions, conversation history, tool inputs, and tool outputs", and large tool outputs "consume significant context" ([same page](https://code.claude.com/docs/en/agent-sdk/agent-loop), "The context window"). A `read_file` on a big file is paid for again on every later turn. Limiting tool output is your first defence; managing the rest is [3.4](/part-03-agents/3.4-context-engineering).
- **Only the model's own words steer it.** There is no hidden plan object. Whatever the model "knows" about its plan is text in the history (or reasoning blocks, which some providers require you to send back; check the provider's tool-use docs when you add thinking).

### Stop conditions

Think of a run as ending in exactly one of a small set of ways. Write them all down before you code; the loop is only as trustworthy as its list of exits.

| Exit | What triggers it | Who decides | Is the answer trustworthy? |
|---|---|---|---|
| Natural stop | The reply has no tool calls (`stop_reason: "end_turn"` on Claude) | the model | as trustworthy as the model's judgement that it's done |
| Turn limit | `turn > MAX_TURNS` | your code | no: the task is unfinished |
| Budget limit | tokens, money or wall-clock time exceeded | your code | no |
| Output cut off | the reply stopped on `max_tokens` / `length` | the API | no: a tool call may be incomplete, so don't execute it ([2.1](/part-02-programming-with-llms/2.1-calling-models#stop-reasons-the-branch-you-always-write)) |
| Refusal or another stop reason | `refusal`, `pause_turn` | the model / API | handle explicitly |
| Fatal error | network failure, bad API key, 4xx on the request | your code | no: fail loudly |

Anthropic's docs make the natural-stop branch explicit: the loop "exits on any other stop reason (`"end_turn"`, `"max_tokens"`, `"stop_sequence"`, or `"refusal"`)", meaning Claude "has either produced a final answer or stopped for another reason that your application should handle" ([How tool use works](https://platform.claude.com/docs/en/agents-and-tools/tool-use/how-tool-use-works)). So "no tool calls" is necessary for a natural stop, not sufficient: look at *why* the model stopped before treating the text as an answer.

**Turn limits are part of the design, not an afterthought.** An agent that can call tools can call them forever: repeating the same failing command, reading file after file. The Agent SDK exposes this as `maxTurns` (default: no limit) and a spend cap `maxBudgetUsd`; when either trips, the run ends with a result subtype `error_max_turns` or `error_max_budget_usd` and no final answer, and its docs call a budget "a good default for production agents" ([How the agent loop works](https://code.claude.com/docs/en/agent-sdk/agent-loop), "Turns and budget"). Note how the SDK counts: a turn is one pass through the loop, "each turn with tool calls, plus one for the final text-only response". Decide your own convention and write it down. Also decide what happens at the limit: throw, or return a structured "I ran out of turns, here is what I did" value. A distinct exit status, rather than a plain string, lets the caller (and, later, your evals) tell a finished run from an abandoned one.

A useful extra signal is **repetition detection**: the same tool with identical arguments three turns in a row is almost never progress. You don't need it on day one, but your step log (below) is what would reveal that you do.

### Tool failures are inputs to the next turn

Chapter 2.6 established that errors are results, not exceptions, and gave the four places a tool call can go wrong. In the loop that rule matters more, because the model's next move depends on what it reads back:

- **Never let an exception escape `runTool`.** Catch it and send the message back as the tool result (on Claude with `is_error: true`; elsewhere the text itself must say it failed). The tool-use tutorial's wording: send the error "back with `is_error: true` instead of crashing. Claude reads the error and can retry with corrected input, ask the user for clarification, or explain the limitation" ([Build a tool-using agent](https://platform.claude.com/docs/en/agents-and-tools/tool-use/build-a-tool-using-agent)).
- **Make the message instructive.** `ENOENT: no such file 'beta.txt'` lets the model guess; the same line plus a directory listing lets it recover.
- **Always answer every tool call**, including the ones you refuse or skip. A call without a result is a malformed history.
- **Distinguish a tool failing from your loop failing.** A shell command that exits non-zero is a *normal result* for the model to read (the test suite failed, which is the information it wanted). A crashed HTTP request to the model is yours to retry or abort.
- **Bound output.** Truncate large results with a marker that says how to get more.

The Agent SDK has the same philosophy: when a tool call is denied, "Claude receives a rejection message as the tool result and typically attempts a different approach or reports that it couldn't proceed" ([How the agent loop works](https://code.claude.com/docs/en/agent-sdk/agent-loop), "Tool execution"). Failure is part of the conversation.

A subtle one for `run_shell`: it is arbitrary code execution, directed by text a model produced, which may itself have been influenced by file contents it read. For this practice, run it in a scratch directory, keep a short allowlist or ask for confirmation on anything that writes, and see [Part 8](/part-08-production/8.1-prompt-injection) for why.

### Log every step

An agent run you can't see is a run you can't debug. The step log is the project's first real feature, and it pays back at once, in 4.1 (error analysis on real runs) and 4.7 (tracing). Log, per step, enough to reconstruct what happened:

| Field | Why |
|---|---|
| run id, turn number, timestamp | order, and to join log lines |
| model and its `stop_reason` / `done_reason` | which exit the loop took |
| text the model produced, tool name, arguments | what it decided |
| result (truncated) and whether it was an error | what it saw |
| tokens in/out for the turn, wall-clock time | cost and latency per step; local and paid models differ a lot |

Append one JSON object per line to a file (JSONL), and print a compact human version to the terminal. JSONL survives crashes, can be tailed, is trivially filtered with `jq`, and later becomes the raw material for your eval set. Mind secrets: log tool arguments and results, but never the API key, and know that file contents you read end up in the log.

Anthropic's agent-building guidance gives the reason beyond debugging: agents should "gather context, take action, verify work", and the third step only works if the loop feeds the model real feedback to verify against ([Building agents with the Claude Agent SDK](https://claude.com/resources/articles/building-agents-with-the-claude-agent-sdk)). The log is how *you* verify the verification.

### Local versus paid models inside the loop

The loop is identical for every model; the models are not. I ran a throwaway loop (about 30 lines, `fetch` to Ollama's native `/api/chat`, `read_file` and `run_shell`, `think: false`, temperature 0, no paid calls) in a directory with one file, `a.txt`, containing `alpha=1` and `beta=2`, and asked: "Which file in this directory contains beta, and what is the value of beta?" Same prompt and tools, two local models:

| | `qwen3:8b` | `qwen3:14b` |
|---|---|---|
| Turn 1 | `read_file("beta.txt")`: guessed a filename, got ENOENT | `run_shell(find . -type f -exec grep -l "beta" {} \;)`: searched first |
| Turn 2 | `run_shell(find ... grep -l beta)` found `./a.txt` | `read_file("./a.txt")`: read it |
| Turn 3 | Stopped with no tool call: "`a.txt` contains the word beta. The value of `beta` is not specified in the file." | Stopped: "`a.txt` contains `beta`, and its value is `2`." |
| Outcome | wrong value; stopped without ever reading the file | correct, one fewer wasted call |

One run each, so this shows a kind of failure, not a rate. But it is worth reading closely, because the failure is the interesting part. `qwen3:8b` handled the tool protocol perfectly: valid calls, a sensible recovery after the error, a clean stop. What it got wrong was *judgement*: it declared done with the evidence half-collected, and it claimed something the file would have contradicted. Your loop sees a perfectly normal natural stop. Nothing in the loop's mechanics can tell the difference, which is why 4.x is about evals. Separately, on a missing-file prompt (`config.yml`), the same model correctly reported the file doesn't exist after one error result, which is the instructive-error pattern working. Timings: the first call of each run took 2 to 8 seconds (model load), later turns roughly 1 second on this machine.

Things to watch for when you run your own loop on a local model and then on a paid one:

- **Malformed or hallucinated calls.** Invalid JSON arguments, a tool that doesn't exist, wrong argument names. Your dispatch has to survive them and report back.
- **Premature stopping.** The example above. The model answers from priors instead of reading.
- **Not stopping.** Repeating a call, or calling a tool after already having the answer. This is what the turn limit is for.
- **Narrating instead of calling.** Writing "I will now read the file" and ending the turn with no tool call. Your loop, correctly, stops.
- **Parallel calls.** Some models emit several calls per turn, some always one. Handle a list either way ([2.6](/part-02-programming-with-llms/2.6-tool-calling#parallel-tool-calls)).
- **Thinking mode.** Reasoning models spend tokens before each call; locally that multiplies the time per turn ([Part 1](/part-01-how-llms-work/1.10-reasoning-models)). The experiment above turned it off.
- **Context length.** Locally, the context size is whatever `num_ctx` you run with (you measured its effect in experiment 10), and an accumulating history can outgrow it. Long tool outputs make this arrive sooner; check what your runtime does when the history no longer fits.

For which paid models to try and what they cost, see [Landscape](/landscape). Run the same goal on a local and a paid model and compare turn counts and where each went wrong. The point is to see the gap in your own log.

### What the loop does not give you (yet)

Your first loop has no planning, no permission checks, no context management, no retries on API errors, and tools that are deliberately basic. Each is a later chapter: tool design ([3.3](/part-03-agents/3.3-tool-design)), context ([3.4](/part-03-agents/3.4-context-engineering)), memory ([3.5](/part-03-agents/3.5-memory)), tracing ([4.7](/part-04-evals-observability/4.7-tracing)), permission prompts in a harness ([5.4](/part-05-harnesses/5.4-mini-harness)). When [3.11](/part-03-agents/3.11-agent-sdks) introduces SDKs, you'll recognise what they wrap. Resist adding features now: you want a loop small enough to hold in your head.

## Practice

**Brief:** Start `project/`: a TypeScript CLI agent with `read_file` and `run_shell` tools, a loop that runs until the model stops calling tools, and a step log. Run it with local Qwen and one paid model, and write where the local model breaks in `notes/agent-loop.md`. You write all the code; I haven't provided any.

**Where:** a step in the growing `project/` (see `project/ROADMAP.md`, step 1). The notes go in `notes/agent-loop.md`.

**Steps:**

1. **Set up the project.** In `project/`: `npm init -y`, `"type": "module"`, and scripts run with `node --env-file-if-exists=../.env src/agent.ts` (Node runs TypeScript directly, as in your experiments). Add `zod` if you want to validate tool arguments. No agent framework, no SDK. Call models with raw `fetch`, as in 2.1.
2. **Pick one wire format first.** Start with local `qwen3:8b` through Ollama's native `/api/chat` (`think: false`, so turns are fast), or its OpenAI-compatible endpoint if you want one code path for both local and paid models. Decide and write down in the README which, and what the message shapes are.  The 2.6 comparison table lists the differences.
3. **Write two tools:** `read_file(path)` and `run_shell(command)`. Each takes validated arguments and returns a string. Neither may throw into the loop. Put a size cap on returned text, with a truncation marker.
4. **Predict before you run.** In `notes/agent-loop.md`, write your guesses: how many turns will "which files in this directory mention "beta", and what do they say?" take; where will qwen3:8b go wrong; what will differ with a paid model?
5. **Write the loop.** `messages` array, call, append the reply, branch on tool calls, execute, append results, repeat. Exit when the reply has no tool calls. Print the final answer.
6. **Add the exits.** A `--max-turns` flag (default something sensible, such as 10) and a distinct, printed exit status for each way a run can end (finished, turn limit, API error, cut-off reply). Check the reply's stop reason and don't execute calls from a cut-off reply.
7. **Add the step log.** JSONL, one line per model call and per tool call, with the fields from the table above, plus a one-line summary at the end (turns, tokens if the API reports them, wall-clock time, exit status).
8. **Run a local battery.** Use at least four goals in a scratch directory, including: one that needs two tools in sequence, one that names a file that doesn't exist, one that needs a command that fails (non-zero exit), and one that can't be finished in your turn limit.
9. **Run the same goals on one paid model** (a cheap one from [Landscape](/landscape); keep it to a handful of runs and record the spend in `costs.md`). Compare turn counts, the first wrong step and the exit status.
10. **Break it on purpose,** one at a time: (a) remove the line that appends the assistant message and see what the next request does; (b) return a raw exception string from a failing tool and then an instructive one, and compare the model's next move; (c) set `--max-turns 1`.
11. **Write `notes/agent-loop.md`:** predictions and what was wrong, a table of the failures you saw per model (what the model did, which turn, how your loop reacted, what you'd change), and answers to: which failures can the loop itself catch, and which only an eval or a human could?
12. **Commit.** `project/` is yours from here on; later chapters extend it.

**Done when:**

- `node src/agent.ts "<goal>"` (adjust to your layout) runs against local Qwen and against a paid model, loops until the reply has no tool calls, and prints the final answer.
- A run never exceeds `--max-turns`, and each way of ending prints a different status.
- A failing tool, a missing file and a non-zero shell exit each produce a tool result the model reads and reacts to, and the program doesn't crash.
- Every run leaves a JSONL log you can read with `jq` and use to reconstruct what the model did.
- `notes/agent-loop.md` names at least two concrete places where the local model broke or diverged from the paid one, with the log lines that show it, and your answer to which of them the loop could have caught.

## Check questions

1. The loop's last line before repeating is "append the tool results". What exactly goes wrong if you skip appending the assistant message that contained the tool calls?

   <details><summary>Answer</summary>

   The next request contains a tool result with no matching tool call in the history (on Claude, a result whose `tool_use_id` has no `tool_use` before it), which providers reject as a malformed conversation, and even where it's accepted the model can't see what it asked for. The history is the agent's only state, so what's missing is simply gone.

   </details>

2. List the ways a run can end and say, for each, whether you can trust the output as an answer.

   <details><summary>Answer</summary>

   A natural stop (no tool calls) gives an answer that's only as good as the model's judgement; the 8b example above stopped early and wrong. A turn or budget limit means the task is unfinished. A cut-off reply (`max_tokens`/`length`) means a tool call may be incomplete, so raise the limit and redo it. Refusals and `pause_turn` need explicit handling. A fatal API error means no answer at all. Each deserves its own status so callers and evals can tell them apart.

   </details>

3. A tool throws `FileNotFoundError`. Compare two designs: the exception propagates and ends the program, versus the loop catches it and appends it as the result. When might each be right?

   <details><summary>Answer</summary>

   Catching and returning it is the default: the model can recover, as the missing-file run showed, and the failure becomes data in the log. Letting it propagate is right only for failures the model can't help with, such as a bug in your own harness, a bad API key or a network failure to the model API, which should fail loudly. The distinction is whether the failure is a fact about the world the model is acting on, or about your program.

   </details>

4. Your local model finishes in three turns with a confident, wrong answer. The loop reported a natural stop. What does that tell you about what a loop can and can't guarantee, and what would you add?

   <details><summary>Answer</summary>

   The loop guarantees mechanics (limits, error handling, logging), not correctness: a natural stop only means the model chose to stop. To catch this class of failure you need something that checks the result against ground truth, such as a code-based check or a verification step the task provides (run the tests), an eval on logged runs (Part 4), or a human. Prompting the model to verify, or giving it a tool that makes verification cheap, can reduce it but not remove it.

   </details>

5. Why does a long agent run get more expensive per turn, even if every tool result is small?

   <details><summary>Answer</summary>

   Every request re-sends the whole `messages` array plus the tool definitions, so the input grows with each turn and the total input over a run grows faster than linearly. Caching of the unchanged prefix reduces the price but not the length, and long contexts can also degrade quality. That is the problem 3.4 addresses.

   </details>
