# Harness comparison

## Why this matters

Claude Code, Codex CLI, opencode, Aider and Cline/Continue make different bets: how much of the repository to put in front of the model, how to let it edit, how much to trust it, and which models to allow. Reading feature lists will not tell you which bets matter for *your* work, because every product claims to do all of it. Running the same tasks through several of them will.

This chapter gives you the comparison criteria (they are the components from [5.1](/part-05-harnesses/5.1-what-is-a-harness), with model support added), a documented profile of each harness, and a method for running a fair comparison. It is deliberately not a ranking. Products change monthly, so a table of "who wins" would be stale before you finished reading it. What lasts is the set of questions and the habit of holding the model fixed while you vary the harness.

**Learning goals**

- Compare harnesses on context handling, tools, permissions and model support
- Run them on the same tasks
- Pick harnesses for different jobs

## Explanation

### Comparison criteria

Take the components from 5.1 and ask one question of each harness.

| Criterion | The question to ask | Why it matters |
|---|---|---|
| **Context handling** | What does the model see by default, how does the agent find more, and what happens when the window fills? | Decides whether the model has the right files, and whether a long session degrades. |
| **Tools and edit mechanism** | How does it change files (whole file, search/replace, patch)? Can it run commands and tests? | An edit that can fail to apply, or a harness that cannot run tests, shapes every result ([3.3](/part-03-agents/3.3-tool-design)). |
| **Permissions and safety net** | What runs without asking? Is there a sandbox, an undo, or only a prompt? | Decides how often the run stalls and how bad a wrong action can be. |
| **Model support** | Which providers and models can it drive, and can it use a local one? | Decides whether you can hold the model fixed across harnesses, and what the run costs ([Landscape](/landscape)). |
| **Automation surface** | Can it run headless from a script, with machine-readable output? | Decides whether you can compare it on a set of tasks without sitting in front of it. |
| **Extension points** | Instruction files, MCP, subagents, custom commands. | Decides how far you can shape it to your project. |

The profiles below fill these in from each project's own documentation. Where a page did not state something, the profile says so instead of guessing. [Landscape](/landscape#coding-agents-and-harnesses) holds the current list of harnesses, their licenses and status changes such as acquisitions.

### Claude Code

Anthropic's agentic coding tool; closed source ([Landscape](/landscape#coding-agents-and-harnesses)). 5.1 already used its docs as the reference anatomy, so only the points that matter for comparison are repeated here.

- **Context.** Automatic compaction into a summary near the limit, a `/context` view, `CLAUDE.md` and memory loaded into every session, skills loaded on demand, and subagents with their own window ([How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)).
- **Permissions.** Permission modes plus allow rules, and file checkpoints you can rewind to (same page). Headless runs have their own rules: in a `claude -p` run in manual mode, a call that needs approval is denied unless a hook or `--permission-prompt-tool` approves it, and `--allowedTools` pre-approves tools by rule ([Run Claude Code programmatically](https://code.claude.com/docs/en/headless)).
- **Models.** Claude models through the Anthropic API, Amazon Bedrock, Google Cloud's Agent Platform, Microsoft Foundry and Claude Platform on AWS ([Model configuration](https://code.claude.com/docs/en/model-config)). Gateways are supported for Claude models, but Anthropic "doesn't support routing Claude Code to non-Claude models through any gateway" ([LLM gateways](https://code.claude.com/docs/en/llm-gateway)). So Claude Code is the one harness here you cannot point at Qwen or GPT and call a fair test of the harness; it is a fixed point to compare the others against.
- **Automation.** `claude -p "..."` runs non-interactively, `--output-format json` returns the result with metadata and cost, and the JSON payload "includes `total_cost_usd`", which the docs call a client-side estimate that can differ from your bill ([headless docs](https://code.claude.com/docs/en/headless)).

### Codex CLI

OpenAI's coding agent for the terminal, Apache-2.0, written in Rust ([repository](https://github.com/openai/codex)). You sign in with ChatGPT or use an API key (README, same page).

- **Permissions are its signature.** Two separate dials. The **sandbox mode** limits what commands can touch: `read-only`, `workspace-write` (edit and run in the working directory, network off unless enabled) or `danger-full-access` (no sandbox; together with no approvals it is the `--yolo` setting the docs mark not recommended). The **approval policy** decides when it asks: `on-request` (asks before editing outside the workspace or running commands that need network), `never`, or `granular`. "By default, the agent runs with network access turned off" ([Agent approvals and security](https://learn.chatgpt.com/docs/agent-approvals-security)). The sandbox is enforced by the operating system, not by a prompt, which is the contrast with prompt-only permission checks that 5.1 and [5.2](/part-05-harnesses/5.2-harness-anatomy) draw. Separate `linux-sandbox` and `bwrap` crates sit in the [source tree](https://github.com/openai/codex/tree/main/codex-rs).
- **Context.** `/init` creates an `AGENTS.md` and the interface shows how much context is left ([Codex CLI docs](https://learn.chatgpt.com/docs/codex/cli)). The source has compaction modules, as 5.2 notes.
- **Models.** The docs page for the CLI shows `/model` choosing a model and reasoning effort. Local models are documented: `--oss` runs against a local provider, Ollama or LM Studio, chosen with `--local-provider` or `oss_provider`, and other endpoints can be added as custom entries under `model_providers` ([Advanced configuration](https://learn.chatgpt.com/docs/config-file/config-advanced)). The source tree has matching `ollama` and `lmstudio` crates ([tree](https://github.com/openai/codex/tree/main/codex-rs)).
- **Automation.** `codex exec "..."` runs non-interactively, streams progress to stderr and prints only the final message to stdout; `--json` gives a JSON Lines event stream, `-o` writes the last message to a file, and `--sandbox workspace-write` allows edits (the default is read-only). It must run inside a Git repository unless you pass `--skip-git-repo-check` ([Non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode)).

### opencode

Open source (MIT) coding agent with a terminal UI, desktop app and web mode ([opencode docs](https://opencode.ai/docs/), [Landscape](/landscape#coding-agents-and-harnesses)). 5.2 read its source; here is the comparison view.

- **Models are its signature.** `/connect` adds credentials for built-in providers (from the models.dev catalog) and `/models` picks one. Ollama needs no connection: opencode "probes `http://127.0.0.1:11434`, discovers completion models, and adds them to `/models`", and any other OpenAI-compatible runtime can be added as a custom provider ([Providers](https://opencode.ai/docs/providers/)). That makes it the easiest of the five to run against your local Qwen models and against several paid providers with the same interface.
- **Agents as permission sets.** The built-in `build` agent is the default coding agent; `plan` explores without editing normal project files; `general` and `explore` subagents run in child sessions with fresh context ([Agents](https://opencode.ai/docs/agents/)). Rules are `allow`, `ask` or `deny` per tool, as 5.2 showed in the source ([Permissions](https://opencode.ai/docs/permissions/)). The source I read in 5.2 did not contain an operating-system sandbox, so its safety rests on those rules.
- **Context.** Compaction with a summary template and cache-aware precompute (5.2).
- **Automation.** `opencode run "..."` submits a prompt without the interactive interface, "for scripts, CI jobs" ([CLI docs](https://opencode.ai/docs/cli/)). The page does not list the flags for model or output format, so read `opencode run --help`.

### Aider

An older, different design: **pair programming in the terminal**, built around git ([aider.chat](https://aider.chat/), [Landscape](/landscape#coding-agents-and-harnesses)). Most of its bets differ from the agent-loop harnesses above, which makes it the most instructive contrast.

- **Context is explicit and ranked, not searched.** You put files in the chat with `/add` (editable) or `/read-only`, free space with `/drop`, and check usage with `/tokens` ([commands](https://aider.chat/docs/usage/commands.html)). On top of that Aider sends a **repo map**, "a concise map of your whole git repository" with key classes and functions, ranked by a graph algorithm over file dependencies so only the most relevant part is sent, within a token budget set by `--map-tokens` that "defaults to 1k tokens" ([Repository map](https://aider.chat/docs/repomap.html)). Contrast this with Claude Code and opencode, where the model decides what to open.
- **Edit formats are a first-class setting.** The model returns edits in a format Aider parses: `whole` (a full updated copy of each file), `diff` (search/replace blocks), `udiff`, `diff-fenced` (mainly for Gemini models) and the `editor-*` variants ([Edit formats](https://aider.chat/docs/more/edit-formats.html)). The format is chosen per model because models differ in which one they follow reliably, a concrete case of the model-harness co-design from 5.1.
- **Modes.** `code` (default), `ask` (discuss, never edit), `architect` (an architect model proposes, an editor model writes the edits) and `help` ([Chat modes](https://aider.chat/docs/usage/modes.html)). Architect mode is the two-model split that opencode and Claude Code do with subagents, done inside one command.
- **Safety net is git, not a sandbox.** "Whenever aider edits a file, it commits those changes with a descriptive commit message", it commits your uncommitted work separately first, and `/undo` discards the last change ([Git integration](https://aider.chat/docs/git.html)). Nothing in the docs I read describes a command sandbox. With `--test-cmd` and `--auto-test` it runs your tests after each edit and tries to fix failures; it lints edited files by default ([Linting and testing](https://aider.chat/docs/usage/lint-test.html)). That is verification built into the loop's edges.
- **Models.** Works with "most LLMs", including local models and OpenAI-compatible endpoints; the page's recommendations are a list of older model names, so treat it as dated and look at the [leaderboards](https://aider.chat/docs/leaderboards/) for current results ([Connecting to LLMs](https://aider.chat/docs/llms.html)).
- **Automation.** `aider --message "..." file.py` makes the change and exits; `--yes` answers every confirmation; `--message-file` reads the instruction from a file ([Scripting](https://aider.chat/docs/scripting.html)).

### Cline and Continue

Both live mainly in the editor. Cline is "an AI coding agent that lives in your editor and your terminal" ([Cline docs](https://docs.cline.bot)); Continue is an open-source assistant for VS Code and JetBrains with Chat, Agent, Edit and Autocomplete modes plus a CLI called `cn` ([Continue docs](https://docs.continue.dev)). Their status differs: [Landscape](/landscape#coding-agents-and-harnesses) records that Continue was acquired by Cursor and its open-source codebase stays available, so treat it as a lower-confidence pick for new work.

- **Cline: Plan/Act.** Plan mode "lets you explore and strategize without changing files"; Act mode can modify files and run commands, and keeps "the full context from your planning session" ([Plan & Act](https://docs.cline.bot/core-workflows/plan-and-act.md)). The separation is a read-only mode enforced by the harness, like opencode's `plan` agent.
- **Cline: permissions.** "Every action requires your explicit approval" by default. The Auto Approve page lets you approve categories (read project files, edit project files, run safe commands, browser, MCP) separately; command safety is not a fixed allowlist but a `requires_approval` flag the *model* assigns to each command, which the docs say is not a guarantee. YOLO mode approves everything and "disables all safety checks"; the docs recommend checkpoints and throwaway environments ([Auto Approve](https://docs.cline.bot/features/auto-approve.md)). That is a different trust model from Codex's: Codex's sandbox bounds what a command *can* do, while Cline's classifier relies on the model's judgement of what a command *will* do.
- **Cline: context and undo.** `@` mentions bring files into the conversation ([Adding Context](https://docs.cline.bot/core-workflows/working-with-files.md)), and Checkpoints let you roll back code changes while keeping the conversation ([Checkpoints](https://docs.cline.bot/core-workflows/checkpoints.md)). For a filling window there are manual commands: `/smol` (alias `/compact`) condenses the conversation into a summary, and `/newtask` hands off to a fresh task with a clean window ([Using Commands](https://docs.cline.bot/core-workflows/using-commands.md)). I did not find a docs page on whether it does this automatically, so test it (see Practice).
- **Cline: models and automation.** Anthropic, OpenAI, Gemini, Bedrock, DeepSeek and OpenRouter, plus Ollama and LM Studio locally ([Authorizing](https://docs.cline.bot/getting-started/authorizing-with-cline.md)). The CLI is `npm i -g cline`; headless mode turns on with `--json`, piped stdin or redirected output, and `--auto-approve`, `-m` and `-P` set approval, model and provider ([CLI overview](https://docs.cline.bot/usage/cli-overview.md)). Note the default: `--auto-approve` is `true` in the CLI, so a headless run edits and executes without asking. Run it on a clean branch.
- **Continue: plan mode.** Chat is for learning, Plan for strategy and Agent for execution; Plan is "a safe, read-only environment" that blocks file edits, terminal commands and commits ([Plan mode guide](https://docs.continue.dev/guides/plan-mode-guide)). Its docs mark the older context providers (`@Codebase`, `@Docs`) as deprecated ([docs home](https://docs.continue.dev)), so older tutorials describe a different product than the current one.

### Side by side

This table compresses the profiles above. It states what the documentation says, not how well each thing works.

| | Claude Code | Codex CLI | opencode | Aider | Cline |
|---|---|---|---|---|---|
| **Context** | Agent searches; compaction; `CLAUDE.md`; subagents | Agent searches; `AGENTS.md`; compaction in source | Agent searches; compaction; child sessions | You pick files; ranked repo map | `@` mentions; checkpoints; manual `/smol` and `/newtask` |
| **Edits** | Own edit tools | Patch-based (an `apply-patch` crate exists) | Exact-match edit tool (5.2) | Model-specific text formats | Tool calls, approved per action |
| **Permissions** | Modes, allow rules, checkpoints | OS sandbox plus approval policy | allow/ask/deny rules per tool and agent | Confirmations; git commit and `/undo` | Per-category approval; model-assigned risk; YOLO |
| **Models** | Claude only (several clouds) | OpenAI by default; local via `--oss`; custom providers | Many providers; Ollama auto-discovered | Most LLMs, local too | Many providers, local too |
| **Headless** | `claude -p` | `codex exec` | `opencode run` | `aider --message` | `cline "..."` / `--json` |
| **Source** | Closed | Apache-2.0 | MIT | Open | Open |

### Method: comparing fairly

A comparison is only informative if the differences you see come from the harness. The rule from [5.1](/part-05-harnesses/5.1-what-is-a-harness#why-the-harness-changes-results) is to change one thing at a time. For harnesses, that gives you a checklist of what to hold fixed.

1. **Same model, where the harness allows it.** Claude Code only runs Claude models. opencode, Aider and Cline can drive the same Claude model through the Anthropic API or OpenRouter. Codex CLI is built around OpenAI models. So you cannot hold the model fixed across all five; you can across three or four. Say which comparisons are model-controlled and which are not, and never attribute a cross-model gap to the harness.
2. **Same task, same starting state.** Start every run from the same commit in a fresh checkout or worktree ([6.5](/part-06-claude-code/6.5-parallel-work) covers worktrees). Keep the task text identical, down to the punctuation.
3. **Same instructions, in each harness's format.** Claude Code reads `CLAUDE.md`, Codex reads `AGENTS.md`, Aider takes extra files via `/read-only`. Put the same content in each, or none in any. A project rule that only one harness reads is a harness difference you introduced.
4. **Comparable permissions.** A harness that stops to ask after every command and one running with approvals off are not doing the same job. Choose the closest settings (edit and run tests allowed, no network, no destructive commands) and write them down.
5. **Grade by outcome, with the same checks.** Use the graders from your eval set ([4.3](/part-04-evals-observability/4.3-code-based-checks)): run the tests, not your impression. Then read the transcripts for *how* it got there.
6. **Record cost and time.** Tokens, dollars and wall-clock time, per run. Some harnesses report cost themselves (Claude Code's JSON output has a cost field); for the others use the provider dashboard.
7. **Repeat.** Model output varies between runs. One run per cell is an anecdote. Run each task at least twice, and treat a gap smaller than the run-to-run spread as noise.

### Picking a harness for a job

The following is my synthesis from the profiles above, not something the vendors claim. Treat it as a starting hypothesis that your own experiment will confirm or break.

| Job | Properties to look for | Candidates to try first |
|---|---|---|
| Day-to-day coding with the strongest model you have | Deep context handling, extension points, tight loop | Claude Code (you already use it), opencode with the same model |
| Unattended or scripted runs | Headless mode, machine-readable output, an enforced boundary | Codex CLI (OS sandbox, `exec --json`), Claude Code `-p` with explicit `--allowedTools` |
| Mixing models, including local | Broad provider support, easy local discovery | opencode, Aider, Cline |
| Small, reviewable, git-native edits | Per-edit commits, explicit file scope, undo | Aider |
| Staying in the editor | Editor integration, read-only planning mode | Cline, Continue |
| Running against an untrusted repository | A sandbox that bounds commands, not a prompt | Codex CLI, or any harness inside a container ([Part 8](/part-08-production/8.3-sandboxing)) |

## Practice

**Brief:** Run three tasks from your eval set in three harnesses, with the same paid model where possible. Compare them in `notes/harnesses.md`: what each does well and how each manages context.

**Where:** `experiments/25-harness-comparison/` (README with a results template, written up by you) and `notes/harnesses.md`. Standalone: no change to `project/`. You write any scripts; there is no starter code. If you use a Python helper for the table, keep it small, but TypeScript is fine.

**Steps:**

1. **Pick the three tasks** from the eval set you built in [4.2](/part-04-evals-observability/4.2-eval-sets) and graded in [4.3](/part-04-evals-observability/4.3-code-based-checks), so each has a code-based check. Choose different kinds: for example a one-file bug fix, a change that spans several files, and a task that needs the agent to run something and read the output. If your eval set has none of these, write the three tasks down with a command that checks the result.
2. **Pick three harnesses.** Claude Code is one (you know it). Choose two of opencode, Aider, Codex CLI and Cline. Install them following their docs, and read each one's headless page first (links above).
3. **Pick the model.** Use the same paid model in as many of the three as possible: Claude Code needs a Claude model, and opencode, Aider and Cline can use it through the Anthropic API or OpenRouter. Codex CLI is built for OpenAI models, so if you choose it, mark that row as not model-controlled. Look at [Landscape](/landscape) for current models and prices, and pick a cheap one for the first pass. Write the model into the README.
4. **Set up identical starting state.** One repo, one commit. For each run create a fresh worktree or copy. Put the same instructions in each harness's file (`CLAUDE.md`, `AGENTS.md`, or `/read-only` for Aider), or have none in any.
5. **Set comparable permissions** (edits and running the test command allowed, no network, no destructive commands) and write the actual settings per harness into the README. Run everything on a clean branch: the Cline CLI defaults `--auto-approve` to `true`.
6. **Run headless.** Use `claude -p`, `codex exec`, `opencode run`, `aider --message` or `cline` with the same task text. Save each transcript or JSON output. Run each task twice per harness, so you get an idea of the run-to-run spread.
7. **Grade by your checks.** Run the eval check for each result. Record pass or fail, wall-clock time, tokens and cost per run. Add every dollar to `costs.md`.
8. **Read the transcripts for context handling.** For each harness, write down what it looked at first, how many files it read, whether it ever lost track or re-read things, whether it hit a compaction, and what it did to verify. For Aider, inspect the repo map with `/tokens` and try one task with and without the files added.
9. **Write `notes/harnesses.md`.** A table (tasks by harnesses: pass rate, time, cost), then one paragraph per harness on what it did well and how it managed context, then a "which job for which harness" list in your own words. Say which cells were model-controlled.

**Done when:**

- `experiments/25-harness-comparison/README.md` states the model for every harness, the permission settings, the three tasks with their check commands, and a results table with at least two runs per cell.
- Every run has a pass/fail from a command, not from your impression, plus time and cost, and the cost appears in `costs.md`.
- `notes/harnesses.md` has one paragraph per harness on context handling, citing something you saw in a transcript.
- At least one difference between harnesses is explained by a harness component (edit mechanism, context loading, permissions), and you say which cells were not model-controlled.

## Check questions

1. Why can't you hold the model fixed across all of Claude Code, Codex CLI, opencode, Aider and Cline, and what do you do about it when you report results?

   <details><summary>Answer</summary>

   Claude Code only drives Claude models (Anthropic does not support routing it to non-Claude models through a gateway), and Codex CLI is built around OpenAI models, while opencode, Aider and Cline can use many providers. So some comparisons are model-controlled and some are not. Report which cells are which, and do not attribute a cross-model gap to the harness.

   </details>

2. Codex CLI has a sandbox mode and an approval policy; Cline has per-category auto-approve with a model-assigned `requires_approval` flag. What is the difference in what each guarantees?

   <details><summary>Answer</summary>

   Codex's sandbox mode is enforced around the commands: `workspace-write` limits where they can write and keeps network off by default, whatever the model intends. The approval policy only decides when to ask. Cline's command classification is the model's own judgement of whether a command needs approval, and its docs say the examples are not guarantees; YOLO mode turns the checks off. A sandbox bounds what a command can do, a classifier predicts what it will do.

   </details>

3. Aider does not let the agent search the repository by default; it sends a repo map. What is the trade-off compared with an agent that greps and opens files itself?

   <details><summary>Answer</summary>

   The repo map is cheap and predictable (ranked, within a token budget that defaults to 1k tokens), and it puts the structure in front of the model without extra tool calls, but it is a summary: you also have to add the files to edit with `/add`, and relevant code that ranks low may be missing. An agent that searches can find anything but spends turns and tokens doing it, and depends on the model choosing good searches. Neither is better in general; test on your tasks.

   </details>

4. You run the same task in two harnesses with the same model, once each, and one passes and one fails. What can you conclude, and what would you do next?

   <details><summary>Answer</summary>

   Very little: model output varies between runs, so one run per cell is an anecdote. Repeat each at least twice, compare to the run-to-run spread, then read the transcripts to see whether a harness component (edit failures, missing context, permission stalls) explains the difference. Also check that the instructions and permissions were truly equivalent.

   </details>

5. Which harness would you reach for to run an unattended script against a repository you do not fully trust, and why? Name the setting you would use.

   <details><summary>Answer</summary>

   One where an enforced boundary limits the commands, for example Codex CLI with `codex exec` in the `workspace-write` or `read-only` sandbox with network off, or any harness run inside a container. Prompt-level permissions alone can be steered by injected text in the repository ([Part 8](/part-08-production/8.3-sandboxing)). Also run on a clean branch, since headless runs with approvals off will edit and execute without asking.

   </details>
